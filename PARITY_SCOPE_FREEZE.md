## Acceptance checklist

### A. Salesforce-like application and builder experience

- [ ] **UX-01 — Setup and app navigation:** Provide coherent Salesforce-like Setup navigation, workspace/app navigation, search/quick-find, deep links, browser history, and return/navigation behavior for every in-scope workspace.
- [ ] **UX-02 — Builder interaction model:** Each builder has a consistent, discoverable canvas/work area, navigation/toolbox, configuration properties, save/run/preview controls, contextual help, selection state, and clear feedback.
- [ ] **UX-03 — Every visible control works:** Buttons, menus, drag/drop, resizers, tabs, filters, pickers, dialogs, toolbar actions, and keyboard-accessible alternatives perform the operation their labels imply; no inert controls or success-shaped placeholders.
- [ ] **UX-04 — Complete UI states:** Loading, empty, draft, saved, active/published, dirty, validation, permission-denied, runtime-error, and success states are explicit and recoverable. Unsaved work is protected from accidental loss.
- [ ] **UX-05 — Usability and accessibility:** Match the reference interaction behavior, terminology, sensible defaults, help, validation placement, responsive layouts, keyboard operation, and accessible names/focus behavior across desktop and narrow-screen use.
- [ ] **UX-06 — Consistency:** Builder previews, saved configuration, runtime pages, APIs, and metadata display the same effective state; no user-facing setting is silently ignored.

### B. Object Manager and metadata-driven data model

- [ ] **OBJ-01 — Object lifecycle:** Search and inspect supported objects; create, edit, and safely delete custom objects; preserve standard-object structural constraints and metadata permissions.
- [ ] **OBJ-02 — Object properties:** Persist labels, API names and immutability rules, descriptions, object features, deployment status, and text/auto-number record-name configuration.
- [ ] **OBJ-03 — Fields and relationships:** Support every field type exposed by the in-scope field builder, its type-specific settings, defaults, required/unique constraints, picklists/dependencies, formulas, lookup/master-detail relationships, history tracking, and editability. Relationship creation must support related lookup criteria that compare a target-object field to either a constant or a field on the source record.
- [ ] **OBJ-04 — Setup metadata:** Make all twelve currently inventoried Object Manager sections functional: Details; Fields & Relationships; Page Layouts; Lightning Record Pages and activation; Buttons, Links, and Actions; Compact Layouts; Field Sets; Object Limits; Record Types; Related Lookup Filters; Search Layouts; and List View Button Layout. The inventory is a minimum, not permission to omit further sections or steps in the agreed Salesforce reference surface.
- [ ] **OBJ-05 — Runtime consumption:** Metadata must drive record forms, list/detail views, actions, lookups, related lists, record types, page/layout assignment, field visibility/editability, search results, compact highlights, and field history where configured.
- [ ] **OBJ-06 — Integrity and safety:** Validate metadata server-side; preserve existing data compatibly; enforce dependencies, stored-value cleanup, deployment rules, tenant isolation, and authorization on every relevant API/runtime path.
- [ ] **OBJ-07 — No false limits:** Object Limits is informational unless a limit is explicitly documented by this frozen reference pack; do not invent edition quotas.

#### Detailed Object Manager acceptance criteria

These criteria expand OBJ-01 through OBJ-07; they do not replace them. “Object Manager parity” covers the object-administration experience in Salesforce Lightning for the standard and custom data objects in the agreed reference pack, including every object-specific section and workflow discovered by the reference inventory. It is not a claim of parity with every Salesforce product, edition, object family, Setup page, or internal implementation.

The baseline references are the Setup/Object Manager tour, the Data Modeling and Object Relationships modules, Formula Fields, Page Layouts and Record Pages, and Compact Layouts in the frozen reference pack; the user's Salesforce New Relationship screenshot is also a direct interaction reference. Before implementation or sign-off, record the date and capture an inventory of the reference UI's object-list actions, object-specific navigation entries, field/relationship wizard steps, and conditional sections for representative standard and custom objects. The inventory must be compared to this list. If a reference exposes another Object Manager section, action, wizard step, field type, or conditional workflow within this boundary, add its acceptance criterion here before declaring the scope complete; the current implementation and this initial list are not evidence that the reference surface is exhaustive.

##### Entry, navigation, object catalog, and lifecycle

- [ ] **OBJ-08 — Object Manager entry and routes:** Reach Object Manager through Setup navigation and supported Quick Find/deep links. Selecting an object opens its configuration; selecting a section opens that section for the same object. Browser back/forward, refresh, direct links, object switching, and return navigation preserve or intentionally resolve the selected object and section without stale drafts or broken routes.
- [ ] **OBJ-09 — Complete object catalog:** List every in-scope standard and custom object visible to the current tenant/user. Search/filter by the reference-supported object identity; make matching, no-results, loading, and permission-denied states explicit. Each row's object label and available actions correspond to that object's actual type and authorization.
- [ ] **OBJ-10 — Create custom object:** The create workflow validates and saves singular/plural labels, API name and naming rules, description/help where exposed, record-name label and type (Text or Auto Number), auto-number display format/starting value where exposed, supported object features, deployment status, and the custom-tab launch option. Generated API names and defaults are shown before save; duplicates, malformed values, and invalid combinations are rejected with actionable field-level feedback. Successful creation initializes usable object metadata and opens the next configured step, including the tab wizard when selected.
- [ ] **OBJ-11 — Edit object properties:** Edit every mutable property exposed for the selected custom object; show immutable properties as read-only with a clear explanation. Saving persists the exact values and updates object navigation, runtime labels, tab metadata, and dependent builders. Standard-object structural properties are read-only or constrained to the same extent as the reference.
- [ ] **OBJ-12 — Custom tab wizard:** When launched from custom-object creation, choose a supported tab style, navigate the wizard's steps, and save or cancel without losing or duplicating the object. A saved tab has the configured icon/style, label, access/navigation metadata where exposed, and opens the object's records. The wizard is not skipped merely because object creation itself succeeded.
- [ ] **OBJ-13 — Safe object deletion:** Delete only eligible custom objects after a clear confirmation and dependency/data-impact warning. Reject standard-object deletion and unsafe deletion with dependencies; when deletion is permitted, consistently remove or clean up the object's records and all dependent metadata/permissions/tabs. Cancellation leaves state unchanged.
- [ ] **OBJ-14 — Save state and failure recovery:** Every object metadata save has dirty/saving/saved/failed states, preserves unsaved edits after failure, reports server validation and authorization errors, prevents duplicate submissions, and does not report success until persisted state is returned.

##### Details and fields & relationships

- [ ] **OBJ-15 — Details coverage:** Details exposes the supported object identity, description/help, features, deployment, record-name, and other reference-inventoried properties. Each editable setting has correct labels, constraints, sensible defaults, help, and round-trip persistence. Settings that gate Activities, Chatter, reporting, or other object features have visible consequences and cannot be disabled while incompatible saved configuration would be orphaned.
- [ ] **OBJ-16 — Field catalog and inspection:** Fields & Relationships lists standard and custom fields with their label, API name, type, and reference-supported status/detail information. Search/sort/filter controls work where shown. Opening a field exposes its actual metadata; system/identity fields and otherwise immutable fields cannot be edited or deleted. Empty and loading states are explicit.
- [ ] **OBJ-17 — Complete field-creation workflow:** The New Field flow follows the reference's field-type selection, type-specific configuration, naming/description/help/default/required/unique stages, review/save behavior, and any conditional next steps. It validates each stage before advancing, supports cancel/back where the reference does, preserves entered values when moving between stages, and persists only on explicit save. A modal that merely saves a metadata object does not count as complete if the reference workflow has further consequential steps.
- [ ] **OBJ-18 — Field-type inventory and behavior:** Inventory every field type available for the in-scope objects in the frozen references and reference UI, including type-specific constraints and supported interactions; do not silently omit a type or show an inert type choice. At minimum, verify the currently exposed Text, Long Text Area, Number, Currency, Percent, Date, Date/Time, Checkbox, Email, Phone, URL, Picklist, Multi-Select Picklist, Formula, Lookup Relationship, Master-Detail Relationship, and applicable Hierarchical Relationship fields. For each type, prove metadata round-trip, record form rendering, input normalization/validation, API/Flow/import write behavior as applicable, and read-only or computed behavior as applicable. Any additional type in the audited Salesforce reference is included or explicitly resolved as out of this frozen boundary before sign-off.
- [ ] **OBJ-19 — Type-specific configuration:** Text length, numeric precision/scale, currency/percent behavior, picklist value sets and restriction, defaults, required/unique settings, descriptions/help text, and all other exposed type-specific options enforce documented ranges and combinations in both UI and API. Defaults are applied consistently at record creation and do not bypass validation; incompatible settings are hidden/disabled with an explanation rather than accepted and ignored.
- [ ] **OBJ-20 — Picklists and dependencies:** Create/edit picklist values, ordering, active/restricted behavior and multi-select semantics. Configure controlling/dependent fields and valid value mappings, reject invalid controller/type combinations, and apply active values and dependencies at runtime and on server writes. Where record types customize values, the effective intersection and defaults are correct for each active record type.
- [ ] **OBJ-21 — Formula fields:** Author expressions and choose return types using the reference-supported editor; field/function/operator insertion aids, syntax/reference validation, save errors, and help work. Invalid references, types, cycles, and unsupported syntax are rejected. Formula results are read-only and are consistently calculated for record create/update, API/import, Flow, and display contexts supported by the platform.
- [ ] **OBJ-22 — Relationship field creation:** The lookup, master-detail, and applicable hierarchical relationship flow identifies the relationship type, target object, field label/API name, relationship/child-relationship identity, and every reference-supported behavior before saving. It explains lookup versus master-detail semantics, requiredness, ownership/sharing implications, deletion/cascade/reparent rules where exposed, and related-list effects. Target-incompatible choices and invalid/cyclic/duplicate relationship metadata are rejected.
- [ ] **OBJ-23 — Inline related lookup filter authoring:** During lookup relationship creation, expose the reference's lookup-filter area and allow one or more criteria to be created, edited, and removed before saving the relationship. Configure the target field, operator, comparison source/value, and Required/Optional behavior. Support constant and source-record-field comparisons, field/operator compatibility, null criteria, and the reference's filter combination/logic controls. The relationship and filter metadata save atomically; cancel/failure leaves neither a partial relationship nor orphan filter.
- [ ] **OBJ-24 — Relationship runtime semantics:** Lookup selection searches only eligible target records; required filters cannot be bypassed by typing, direct API writes, imports, Flow writes, updates, or alternate record forms. Optional filters inform selection without falsely blocking a save, as in the reference behavior. Master-detail requiredness, access inheritance, cascade behavior, related lists, and child record lifecycle match the documented relationship type. Changing/deleting a relationship with dependent records or metadata is guarded and understandable.
- [ ] **OBJ-25 — Field editing and history:** Edit every mutable field property permitted by the reference, preserving the field API identity and compatible stored values. Enabling/disabling history tracking follows object-level prerequisites and documented tracking limits; changes generate history only when configured and honor record/field permissions. Type changes that invalidate saved values fail safely with remediation.
- [ ] **OBJ-26 — Field deletion and dependencies:** Deleting a custom field requires explicit confirmation and is rejected while any formula, filter, relationship, layout, field set, record type, page, action, Flow, or other discovered metadata/record dependency uses it. Dependency inspection names all affected consumers; after permitted deletion, values and access metadata are cleaned up without corrupting unrelated records.
- [ ] **OBJ-27 — Field dependency inspection:** The Field Dependencies action identifies controlling/dependent picklists and all other reference-supported metadata consumers. Links/actions navigate to the relevant configuration where supported; dependencies are derived from persisted metadata, not an incomplete manually maintained list.

##### Layouts, actions, compact layouts, and field sets

- [ ] **OBJ-28 — Page Layout authoring:** Create/edit/rename supported page layouts and sections; configure section labels, columns, ordered unique field placement, and other reference-supported display properties. Add/remove/reorder fields and related lists; configure supported standard/custom actions and custom links. Invalid, duplicate, inaccessible, or incompatible placements are rejected or filtered with explanation; unsaved edits are protected.
- [ ] **OBJ-29 — Page Layout runtime and assignments:** Assign layouts using the dimensions exposed by the reference (including profile and record type where applicable), resolve the effective assignment deterministically for the authenticated user, and use it in create/edit/detail runtime. Required fields omitted from a layout remain discoverable and enforceable. Related lists, actions, links, ordering, and field visibility match saved configuration.
- [ ] **OBJ-30 — Lightning Record Pages integration:** The Object Manager entry opens the correct Record Page/activation experience for the selected object and shows the object's applicable saved pages and assignments. It launches the shared Lightning App Builder, saves/activates through that builder, and reflects resulting assignments/runtime state back in Object Manager. This criterion covers Object Manager integration; the separate PAGE criteria remain authoritative for page authoring internals.
- [ ] **OBJ-31 — Buttons, Links, and Actions:** List and configure the reference-supported standard and custom buttons, links, and actions for the selected object. Custom links validate allowed URLs/merge fields and window behavior; actions validate target fields, values, permissions, and supported behavior. Layout placement controls whether each item appears at runtime. Unsupported actions cannot be saved as if functional; standard actions cannot be impersonated by custom entries.
- [ ] **OBJ-32 — Compact Layout authoring and assignment:** Create/edit/rename compact layouts and choose an ordered, unique, supported field set. Configure the primary/default assignment and every other assignment dimension present in the reference; reject nonexistent layouts, invalid fields, and conflicting assignments. The first/primary field and ordered fields render in record highlights and expanded lookup cards as documented, subject to field permissions. Object Manager changes are reflected in runtime without stale cached layouts.
- [ ] **OBJ-33 — Field Sets:** Create, label/API-name, edit, order, and delete field sets with valid unique fields. Field-set metadata is available to its documented consumers, including permission-filtered record-detail views; consumers respect read access, saved ordering, and empty sets. Deletion and field removal report dependencies and cannot silently invalidate consumers.

##### Record types, lookup filters, search, actions, limits, and remaining sections

- [ ] **OBJ-34 — Record Types:** Create/edit/deactivate/delete eligible record types with unique labels/developer names, active/default state, and available description/process options. Maintain exactly the allowed default/active combination; assign record types by the reference's profile/default model; expose record-type selection in runtime where applicable. Record-type-specific picklist values/defaults apply consistently in setup, record forms, API validation, and Flow.
- [ ] **OBJ-35 — Related Lookup Filters (standalone editor):** For every relationship field, configure multiple filters against fields on its actual target object. Support the audited operators, typed comparisons, null checks, constant or source-field operands, and the reference's Required/Optional and filter-logic behavior. Invalid/missing fields, relationship/target mismatches, incompatible operators, malformed logic, and duplicate identities are rejected. Edits and deletes persist and immediately affect picker behavior.
- [ ] **OBJ-36 — Search Layouts:** Configure ordered fields for every search result, lookup dialog, phone lookup dialog, and additional search layout present in the audited reference. Respect the related object's layout when presenting lookup results, searchable/display fields, empty layouts, and responsive form factor. Search results use these definitions at runtime; hidden/unreadable fields are neither displayed nor searchable to unauthorized users.
- [ ] **OBJ-37 — List View Button Layout:** Choose and order the supported standard/custom buttons shown for this object's list views. Only actions with real runtime behavior and appropriate object applicability are available. Saved configuration is reflected consistently in list-view UI and each corresponding API operation; disabling a button cannot be bypassed through a UI path that the setting is meant to control.
- [ ] **OBJ-38 — Object Limits:** Display accurate, clearly labeled metadata usage for all reference-visible counters. Counts update after create/edit/delete and never imply an undocumented Salesforce edition quota. Any actual enforced capacity must be explicitly present in the frozen references and reported with its scope and behavior.
- [ ] **OBJ-39 — Additional object-specific sections:** Audit the complete reference navigation for each representative standard/custom object rather than assuming the twelve currently listed entries are exhaustive or identical for every object. Include every additional section and supported action shown in the agreed Object Manager reference (for example validation rules or automation/trigger sections if present in the audited target) with its own author/edit/save/delete, validation, permission, dependency, and runtime acceptance criteria. Record any section genuinely outside the frozen reference boundary with the source evidence and explicit disposition; do not omit it silently.

##### Cross-cutting metadata, runtime, access, quality, and evidence

- [ ] **OBJ-40 — End-to-end metadata consumption:** Every setting marked functional has at least one documented consumer and changes that consumer's behavior. Verify object/field labels, defaults, validations, record forms, lookup dialogs, related lists, page layouts, record pages, search, list actions, compact highlights, reports/Flows where supported, and history in the relevant runtime/API paths. Persisting metadata without its promised consumer is incomplete.
- [ ] **OBJ-41 — Server authority and authorization:** Validate the same constraints server-side; client state is never trusted for object/field identities, operators, targets, or permissions. Enforce tenant isolation and object/metadata read/create/edit/delete permissions on every endpoint and runtime path. Apply object CRUD, field-level read/edit, record sharing, and relationship-target access consistently; return explicit authorization/validation errors without leaking inaccessible records or field values.
- [ ] **OBJ-42 — Compatibility and integrity:** Existing metadata/data continues to load through migrations/defaults without silent loss. Validate object/field API naming, uniqueness, relationships, lookup criteria, assignment conflicts, and cross-metadata references before persistence. Writes are atomic across coupled definitions; failure leaves prior persisted metadata intact. Delete/update protections account for all consumers discovered by dependency inspection.
- [ ] **OBJ-43 — Usability and accessibility:** Match reference terminology, step order, defaults, contextual help, confirmation, validation placement, and responsive behavior. Every control has an accessible name, works by keyboard, preserves focus appropriately, and exposes loading/empty/dirty/saving/success/error/permission-denied states. No visible choice is inert, mislabeled, or silently discarded.
