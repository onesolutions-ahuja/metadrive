# UNEEngine

UNEEngine is a metadata-driven CRM and setup workspace. Its interface follows the Salesforce Lightning Setup interaction model: an app header and workspace tabs, Setup Quick Find and navigation, Object Manager configuration, and focused report, dashboard, page, flow, and permissions builders.

The frozen Salesforce parity checklist, including Dashboard Builder criteria, is in [PARITY_SCOPE_FREEZE.md](./PARITY_SCOPE_FREEZE.md).

## Workspaces

- `apps/web` – React + Vite interface
- `apps/server` – Express + TypeScript API

## Quick start

```bash
npm install
npm run dev:web
npm run dev:server
```

Then open the frontend at `http://localhost:5173`. During Vite development, `/api` is proxied to `http://127.0.0.1:3001` so login, API requests, and refresh cookies share the frontend origin without requiring extra CORS origins. Set `METADRIVE_API_PROXY_TARGET` to use a different development API. For deployments where the API is not reverse-proxied under the frontend origin, set `VITE_API_BASE_URL` to its URL.

## Local authentication

The API is tenant-scoped and the metadata workspaces require an authenticated session. Sign in with **email and password only**; email addresses are unique across all tenants, so the API resolves the tenant from the user’s email and puts that tenant identity in the verified access token. Tenant ID is used only when creating the organization, not during login. Configure bootstrap values in the same PowerShell session before starting the API; use your own tenant ID and admin email/password:

```powershell
$env:METADRIVE_BOOTSTRAP_TENANT_ID = "your-tenant"
$env:METADRIVE_BOOTSTRAP_TENANT_NAME = "Your Organization"
$env:METADRIVE_BOOTSTRAP_ADMIN_EMAIL = "admin@example.com"
$env:METADRIVE_BOOTSTRAP_ADMIN_PASSWORD = "a-unique-password-of-at-least-12-characters"
npm run dev:server
```

The issuer supports RS256 signing with `AUTH_PRIVATE_KEY` / `AUTH_PUBLIC_KEY` PEM values or `AUTH_PRIVATE_KEY_PATH` / `AUTH_PUBLIC_KEY_PATH` files. Set `AUTH_ISSUER` and `AUTH_AUDIENCE` for deployment URLs and `AUTH_ACCESS_TOKEN_TTL_SECONDS` / `AUTH_REFRESH_TOKEN_TTL_SECONDS` to override validated token lifetimes. It exposes OpenID discovery and JWKS, issues short-lived bearer access tokens, and rotates HttpOnly refresh cookies. Without bootstrap credentials or a provisioned tenant, sign-in is intentionally unavailable. Tenant provisioning for additional organizations is disabled unless `METADRIVE_PROVISIONING_KEY` is configured. Do not use ephemeral development keys or JSON-file state as a production deployment strategy.

Record endpoints are available at `/api/records/:objectName`, `/api/records/:objectName/:recordId`, and `/api/records/:objectName/:recordId/history` (field history requires object/field history tracking to have been enabled). Record visibility combines object permissions, field permissions, record ownership, per-object sharing defaults, role hierarchy, explicit user/public-group shares, and active owner/criteria-based sharing rules; object View All and Modify All grants bypass record sharing without bypassing field permissions. When hierarchy grants are enabled, role ancestors can read subordinate-owned records even under Private sharing; Public Read Only also grants tenant-wide reads, while Public Read/Write grants tenant-wide reads and edits. Delete remains owner/Modify All scoped. Public groups can include users, roles, roles and subordinates, and nested public groups; nesting cycles are rejected. Owner-based rules share records owned by selected roles and their subordinate roles. Criteria-based rules support All/Any matching and Equals, Not Equals, Contains, Starts With, Greater Than, Less Than, and Is Null operators. Rule evaluation is dynamic, so changes to records, owners, rule status, or group membership take effect without storing stale generated shares. Record type availability is granted through profiles and permission sets, can be muted at the permission-set-group level, and is checked for record creation and record-type changes through both the record API and flows. Record owners, Modify All users, and security administrators can manage manual shares at `/api/records/:objectName/:recordId/shares`; share bodies accept `{ "userId": "..." | "groupId": "...", "accessLevel": "Read" | "Edit" }`. Ordinary record create/update requests cannot set `OwnerId`; ownership is assigned to the creating user. Ownership transfers use `PUT /api/records/:objectName/:recordId/owner` with `{ "ownerId": "..." }` and require object edit permission, an enabled Edit action, Modify All or `security:manage`, and an active target user in the same tenant. Permission, role, and sharing metadata are managed in the security workspace and exposed at `/api/metadata/permissions` and `/api/metadata/roles`, protected by `security:read` and `security:manage`. Metadata writes support `objects:manage`, `flows:manage`, `namedCredentials:manage`, `reports:manage`, `pages:manage`, and `dashboards:manage`; the legacy `metadata:write` grant remains an all-metadata administrative permission. Report row counts and summaries are computed from records visible to the running user. Active autolaunched and screen flows can be started at `/api/flows/:apiName/execute`, with screen interviews continued at `/api/flow-interviews/:interviewId/next`. Scheduled flows run from the API process using the configured IANA time zone (UTC by default) and the configured polling interval (`METADRIVE_SCHEDULE_POLL_MS`, default 30000 ms). Recurring Daily/Weekly runs follow local wall time across daylight-saving changes; a configured start time that does not exist on the start date because of a daylight-saving transition is rejected during validation.

CSV imports use `POST /api/records/:objectName/import` with `{ "records": [...] }`; imports have no application-level row-count cap, are checked against object/field/record-type permissions and validation rules, and are rejected without persisting any rows if validation fails. Contact list-view Add to Campaign uses `POST /api/campaigns/:campaignId/members` with `{ "contactIds": [...] }`; it requires the Contact button to be enabled, Campaign edit access, Contact read access, an accessible active campaign, and deduplicates existing members. `/api/auth/me` returns effective `fieldAccess` and `recordTypeAccess` maps for rendering the signed-in user’s record workspace without replacing server-side permission enforcement.

The RBAC implementation is an evolving Salesforce-inspired model, not a claim of complete Salesforce parity. The frozen three-phase scope and acceptance boundaries are recorded in [RBAC-PARITY-PLAN.md](./RBAC-PARITY-PLAN.md). Dashboard folder audiences support permission-set groups and configurable tenant territory hierarchies; this is not Salesforce Enterprise Territory Management. Queue ownership, queue-specific assignment/notification behavior, external/portal sharing, full territory management, restriction rules, implicit account/contact/opportunity sharing, and broader Salesforce permission surfaces remain outside the current implementation. Run the server API build and RBAC smoke tests with `npm run build` and `npm test --workspace apps/server`.

Dashboard metadata is available at `GET /api/metadata/dashboards`, saved with `PUT /api/metadata/dashboards/:apiName`, and deleted with `DELETE /api/metadata/dashboards/:apiName`. Reads require tenant `metadata:read`; writes and deletes require `metadata:write` and dashboard owner/editor access or `dashboards:manage`. Draft dashboards are visible to their owner, dashboard administrators, and users granted access through their dashboard folder. Deployed private dashboards are visible to their owner, explicitly shared users, members of explicitly shared permission-set groups, folder viewers/editors/managers, and dashboard administrators; deployed dashboards shared with All Users are visible tenant-wide to users with metadata read access. Dashboard filters support All/Any matching logic. Dashboard folders are persisted independently and managed through `GET/POST /api/metadata/dashboard-folders`, `PUT/DELETE /api/metadata/dashboard-folders/:folderId`. Folders may be nested; grants inherited from ancestor folders apply to their descendants. Folder grants target users, public groups, permission-set groups, roles, roles and subordinates, or territories, and provide Viewer, Editor, or Manager access. Territory membership and hierarchy are managed through `GET/PUT /api/metadata/dashboard-territories`, requiring tenant metadata read and `metadata:write` or `dashboards:manage` to update. A territory grant includes members of that territory and its subordinate territories; updating membership takes effect immediately. Editors can edit folder dashboards but cannot alter dashboard-level sharing; managers can manage folder structure and grants. Folders containing dashboards or subfolders cannot be deleted. Existing text-only folder assignments are migrated to private owner folders on server startup. Dashboard data previews use permission-checked record or report execution. Dashboard tables paginate in 10-row pages; report-backed tables load later pages from the report API, while report summaries are calculated across all matching records. Report-backed dashboard filters are revalidated and applied by the server on each run.

Deployed dashboards support user-owned point-in-time snapshots through `GET/POST /api/metadata/dashboards/:apiName/snapshots` and `DELETE /api/metadata/dashboards/:apiName/snapshots/:snapshotId`. Snapshots retain only data visible to the running identity selected at capture time, remain private to the capturing user, record the data-evaluation identity, and preserve built-in metrics, chart buckets, and the first 10 table rows. Registered custom components are captured from their rendered browser DOM; the server sanitizes the markup and the viewer displays it in a sandboxed iframe with a restrictive Content Security Policy. The server never executes registered component code to create or display a snapshot. Dashboard cross-filters support simultaneous selections: selected values for the same object/field/operator are ORed, while separate groups are ANDed. Related-record evaluation follows accessible relationship paths up to three hops and enforces object, field, and record access.

Dashboard subscriptions are managed through `GET/POST /api/metadata/dashboards/:apiName/subscriptions`, `PUT/DELETE /api/metadata/dashboards/:apiName/subscriptions/:subscriptionId`, and `POST /api/metadata/dashboards/:apiName/subscriptions/:subscriptionId/run`. Schedules support daily or weekly delivery at a chosen local time and IANA time zone, with one or more tenant users as recipients. Each recipient gets a separate multipart plain-text/HTML dashboard rendering computed with their current record and field permissions. When enabled (the default), every run also saves a recipient-owned dashboard snapshot; each subscription retains the latest 30 snapshots per recipient. Saved custom components captured by a user are sanitized and sandboxed; scheduled runs do not execute custom React code and mark those components as unavailable in their saved snapshot. Delivery runs through a tenant SMTP Named Credential; the creator must retain `email:send` access. API integration tests verify SMTP protocol delivery against an isolated loopback relay. Actual delivery through a tenant's external SMTP provider requires that provider's live credentials and has not been verified here. Emails link to the dashboard but do not include PDF attachments or implement Salesforce's full subscription feature set. The API records last-run status/error and advances missed runs rather than replaying every missed occurrence.

Dashboard controls currently include 100%-stacked bars/columns, ascending/descending chart category sort, a top-N chart limit, and automatic refresh intervals. Filter controls use typed values for text, numeric, date, date-time, picklist, checkbox, and multi-select picklist fields; multi-select filters support Includes/Excludes over one or more selected values. Invalid operators and values are rejected by the server. Report runs launched with dashboard filters verify that each submitted filter ID, field, operator, and value matches a configured dashboard filter before execution. Supported operations include equality/inequality, contains/starts-with where applicable, numeric/date or lexical greater/less comparisons, and null checks. Dashboard administrators can set a fixed running user, leave the dashboard in logged-in-viewer mode, or enable running-user selection for authorized previews. Users with dashboard-management or View All Data permission can select any active tenant user; users with View My Team's Dashboards permission can select themselves or active users in strictly subordinate roles, not peer roles. The server revalidates every selected identity and applies that identity's object, field, and record permissions to dashboard-specific record and report queries and snapshots, while preserving viewer-specific dashboard and folder access and snapshot ownership. Snapshots record the identity used to evaluate their data. Published dashboards have a standalone viewer route at `/une/dashboards/:apiName`, print styling, and per-table CSV export; report-backed exports page through all matching report rows in 5,000-row requests and abort if the result changes during export. Rich-text widget HTML is sanitized on save and snapshot, rendered in a sandboxed frame, and included in scheduled delivery; image widgets accept HTTPS URLs and accessible alt text and are retained in snapshots and scheduled email.

Dashboard widgets can be reordered, resized across four widths and three heights by pointer or keyboard, and use desktop, tablet, and phone grid breakpoints; saved dashboards and snapshots retain widget dimensions. In the live dashboard, Cartesian charts expose numeric axis bounds, formatted tick labels, axis titles, gridline visibility, top/right/bottom legend placement, formatted values, automatic/inside/outside data-label placement, and Salesforce, colorblind-safe, or monochrome color palettes. Gauges support configurable minimum and maximum bounds plus three color-coded ranges with validated, adjustable percentage boundaries. Chart settings, including palette, axis ranges, and data-label placement, are persisted with chart metadata and snapshots. Tabular/Summary/Matrix report formats and report-backed chart summaries are supported. Grouped reports support Count on selected fields (including nonnumeric columns) as well as Sum/Average/Minimum/Maximum on numeric columns. Numeric formula fields can be selected as report summary operations and dashboard measures; formula expressions are recalculated for the active execution user on live dashboard data, report runs, snapshots, cross-filter evaluation, and scheduled delivery. Salesforce-specific chart options and visual equivalence with Salesforce's full chart formatting behavior have not been independently verified; broader report semantics and dashboard controls remain parity gaps.

Reports are tenant-scoped metadata available at `GET /api/metadata/reports`, saved with `PUT /api/metadata/reports/:apiName`, run with `POST /api/reports/:apiName/run`, and deleted with `DELETE /api/metadata/reports/:apiName`. Report execution applies object, record, and field permissions and supports paged results. Deleting a report is blocked while a dashboard references it.

### Global Custom Component Library

Open **Setup → Platform Tools → Global Component Library** to register a self-contained React component from a `.jsx` or `.tsx` file, optionally with a `.css` file. The component must have a default export and cannot import external modules. CSS selectors are scoped to the component wrapper. Choose whether the component should appear in the Lightning page builder, dashboard builder, or both. Choose **Free Canvas** when creating a Home Page to set the canvas width/height in CSS pixels, place custom components by dragging them or editing their pixel position and size, and assign the page to an app or app/profile. Free Canvas components receive a `flows` list of Screen Flow API names/labels/status and may start one with `props.onLaunchFlow(flowApiName)`. The shared registry is platform-wide; page and dashboard placements are saved in each tenant's metadata. Updating a component publishes a new version to every tenant using it, and deleting a component is blocked while any tenant page or dashboard references it.

Only users granted the `components:manage` system permission can register, update, or delete components. Registered code executes in the signed-in user's workspace, so grant this permission only to trusted administrators. Registry reads require `metadata:read`; page and dashboard placement saves continue to require the tenant's `metadata:write` permission. The registry API is `GET/POST /api/component-library` and `PUT/DELETE /api/component-library/:apiName`.

### Named Credentials and Flow HTTP Callouts

Configure a 32-byte AES key and active key ID in the API process before creating or rotating credentials. For example, generate an encryption key with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"` and configure:

```text
METADRIVE_CREDENTIAL_KEYS={"key-2026-10":"<base64-encoded-32-byte-key>"}
METADRIVE_CREDENTIAL_ACTIVE_KEY_ID=key-2026-10
```

Keep these environment values in the deployment secret store; never commit them or put them in tenant metadata. Every tenant's Named Credentials are stored separately and encrypted with AES-256-GCM using tenant-and-credential-bound authenticated data. API responses only return non-secret configuration and whether a secret is present. Blank secrets on edit preserve the stored secret. To rotate encryption keys, add the new key to `METADRIVE_CREDENTIAL_KEYS` and make its ID active, then use **Rotate Key** for each credential; retain old keys until every credential that uses them has been rotated. Rotating an external service's password/token is a separate operation: enter the new secret when editing the Named Credential.

HTTP Callout elements use an existing tenant Named Credential, HTTPS, a relative path, optional templated headers/body, and optional Flow output resources for response and status. Redirects, raw endpoint URLs, local/private/reserved destinations, credentials embedded in URLs, unsafe headers, oversized bodies/responses, and calls exceeding 15 seconds are rejected. The runtime resolves DNS and pins the checked public address for the request. Named Credential APIs are `GET/POST /api/named-credentials`, `PUT/DELETE /api/named-credentials/:id`, and `POST /api/named-credentials/:id/rotate`; all require authenticated metadata read/write permission.

Flow **Send Email** actions and reusable **Email Alerts** use SMTP Named Credentials configured in Flow Builder Manager with an `smtp://host:port` URL and Basic (username/password) or unauthenticated SMTP. Email Alert definitions are tenant-scoped metadata associated with an object, credential, From address, recipients, subject, and plain-text body; they can be selected by record-triggered flows for that object and cannot be deleted while referenced by a flow. TLS is required (implicit TLS on port 465; STARTTLS on supported submission ports), local/private/reserved SMTP hosts are rejected, and the running user must have the `email:send` system permission. Recipients, subject, and plain-text body support Flow record references; delivery failures follow the element's fault connector or fail the interview. Salesforce Email Template entities, template folders, rich-text rendering, and Salesforce recipient-targeting semantics are not implemented. HTTP Callout execution requires the running user's `callouts:execute` system permission and an HTTPS Named Credential or authorized Integration Connection; `FAULT_PATH`, `CONTINUE`, and `FAIL` have distinct tested behavior. Response and status mapping are stored in declared Flow resources. **Submit for Approval** checks requester/approver record access and creates durable approval work items with approve/reject decisions and result notifications; Setup supports reusable single-step approval processes selectable in Flow Actions. Process deletion is blocked for references or pending requests, and deactivation is blocked while an Active Flow references the process. Multi-step approval routing, record locks, and final record actions are not implemented.

Record-triggered flows run synchronously when records are changed through the record API; before-save flows support `$Record` field assignments and decisions, while after-save flows can run supported data elements and create durable scheduled paths relative to Date/DateTime fields. Scheduled paths resume through the persisted Flow interview scheduler. API record creates/imports and Flow DML use a tenant-scoped working copy, so an unhandled in-transaction Flow error rolls back those record changes and Flow DML together; diagnostic failure logs are retained. Autolaunched flows can be invoked by API, and screen flows pause for user input through persisted, expiring interviews with conditional visibility and back navigation. Flow entry and data-element conditions support All/Any and validated custom condition logic. Formula evaluation supports a tested subset of operators and functions, including short-circuit logical evaluation, record-triggered `ISNEW`/`ISCLONE`/`ISCHANGED`/`PRIORVALUE`, date/time arithmetic and construction, timezone offsets and milliseconds, string and picklist helpers, `CASE` branch evaluation, HTML/JavaScript/URL encoding, guarded `HYPERLINK`/`IMAGE` output, bounded regular expressions, numeric and trigonometric functions, and `GEOLOCATION`/`DISTANCE` in miles or kilometers. Flow and record formula evaluation use the running user's configured IANA time zone and BCP 47 locale for date/time conversion and extraction, date-only boundaries, and numeric `TEXT`, `VALUE`, and `ISNUMBER` behavior; local date-times in daylight-saving gaps are rejected. Formula expressions are limited to 10,000 characters and 2,000 tokens, and generated text to 100,000 characters. Tenant admins configure the corporate currency and active currency conversion rates in Company Information (`security:read`/`security:manage`); `CURRENCYRATE(code)` returns corporate-currency units per one unit of the specified active currency, and `CONVERTCURRENCY(value)` converts from the record currency (or corporate currency when there is no record currency) to the running user's configured currency. User currencies must remain active in the tenant's currency settings. The formula catalog and Salesforce-specific coercion rules are still being audited against [the frozen parity checklist](./PARITY_SCOPE_FREEZE.md); functions requiring report grouping, session/authentication secrets, or unavailable org context are not provided, and `ISNEW`/`ISCHANGED`/`PRIORVALUE` require record-triggered context. Record create accepts `cloneFromId` to create a clone from a readable record, copying only fields the caller can both read and edit while recalculating formulas and excluding owner, formula, auto-number, and audit fields. Lookup validation, required related-lookup filters, master-detail cascade deletion, and guarded Named Credential HTTP Callouts are implemented. Wait and schedule dispatch retries persist across process restarts with exponential backoff; recurring scheduled runs catch up one occurrence at a time after the last persisted success. Dispatch is coordinated only within a single API process: the JSON-backed store does not provide atomic distributed claims or multi-instance exactly-once execution. Lookup deletion policies and full distributed asynchronous execution semantics remain under audit. Outbound calls have external side effects and cannot be rolled back if later flow work fails. The remaining Flow, Page, Report, Dashboard, metadata/component, and RBAC acceptance work is tracked only in [PARITY_SCOPE_FREEZE.md](./PARITY_SCOPE_FREEZE.md). Page-layout metadata is distinct from Lightning Record Page activation; tablet is a responsive preview, not a separate Salesforce form-factor activation target.
